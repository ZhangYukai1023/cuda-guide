# 第 35 章：单机多 GPU

[全书导航](../../README.md) · [原始大纲](../../outline.md) · [上一章](../ch34-random-particles/README.md)

本章把四张 32×24 的合成灰度图分给两张 GPU，各设备独立执行亮度变换和局部求和，再合并结果。[multi_gpu_images.cu](examples/multi_gpu_images.cu) 包含 CPU 分区自检、单卡基线、双卡并行任务、P2P 能力查询、P2P 或主机中转合并，并逐像素、逐设备、全局与 CPU 参考比较。源码已在 zyk 用 nvcc 12.8 独立编译；CPU 分区自检通过，当前只有一张可见 GPU，双卡 CTest 实际显示 `Skipped`。双卡 kernel、P2P 与合并均未实测，见[验证记录](results/validation.md)。

## 1. 划分数据与设备资源

图片编号 `0..3`，所有者为 `image % 2`。GPU 0 处理 0、2，GPU 1 处理 1、3；本地批次索引为 `image/2`。输入像素确定性生成，变换为 `clamp(input * (1.1+0.1*image) + 0.05, 0, 1)`。CPU 参考按全局图片编号计算相同的像素和总和。`--selftest` 完全在 CPU 检查每张图片恰好归一个设备、局部布局没有错位，并打印期望总和；它能在没有双卡的环境中运行，但只证明分区逻辑。

双卡路径首先枚举设备，分别创建设备 0/1 的 stream、输入缓冲、输出缓冲和双精度局部求和缓冲。`cudaSetDevice` 后创建/使用该设备资源，避免把一个设备的指针误传给另一个设备的 kernel。单个主机线程依次提交两个设备的工作，再分别同步、下载、验证；设备执行可并行，主机准备和普通 pageable Host 拷贝没有承诺重叠。每设备的局部和用双精度 `atomicAdd` 汇总，结果可能因原子顺序有末位浮点差异，所以检查容差而非逐 bit 相等。代码先在 GPU 0 上处理四张图，作为**正确性单卡基线**，再做双卡路径；当前没有正式重复计时，不能声称双卡加速。

每个设备可能有不同计算能力、显存容量、带宽和繁忙程度。这里只按图片数量 2:2 静态均分；若图像尺寸或处理成本不同，应基于像素数、历史耗时或任务队列分配。`CUDA_VISIBLE_DEVICES` 会重映射程序中的逻辑设备 0/1，运行记录要保留可见设备列表及实际 GPU 型号。多主机线程可以让每个线程固定一个设备并行准备/提交；多进程则各有上下文和故障边界，跨进程还要处理通信与 IPC。本例只实现单主机线程管理两设备，避免把未展示的方式说成已验证。

## 2. P2P、拓扑与合并

程序查询 `cudaDeviceCanAccessPeer(0,1)` 和反向 `1,0`，分别报告。两个方向可能不同，不能只查询一次。若设备 0 能访问设备 1，代码在设备 0 启用 peer access，用 `cudaMemcpyPeer` 将设备 1 的**一个局部和**拷到设备 0，再由设备 0 kernel 合并两个局部和；最后下载结果。若该方向不支持 P2P，则从两个设备各下载局部和，在主机相加。无论走哪条路径，都要与 CPU 全局参考比较。这里只传 8 字节，是功能演示；启用 P2P、同步和复制的固定成本通常超过传输本身，不能据此判断 P2P 性能优势。

“两卡可见”不等于“可以直连”：PCIe/NVLink、同一或不同 CPU socket、IOMMU、驱动和拓扑都会影响 P2P 能力与带宽。实际机器可查看 `nvidia-smi topo -m` 和 CUDA P2P 查询结果。若要合并整张图，可用 peer copy；若只是求全局和，传一个标量更合适。任务之间的依赖必须显式同步：代码先等待设备 1 的计算完成，再复制其局部和，避免读取未写完的数据。对于异步 peer copy，则需用跨设备事件/主机同步正确建立依赖。

## 3. 构建、跳过与运行

在远程仓库根目录：

```bash
cmake -S chapters/ch35-multi-gpu/examples -B build/ch35 \
  -DCMAKE_CUDA_COMPILER=/home/zhangyukai/.local/cuda/bin/nvcc \
  -DCMAKE_CUDA_ARCHITECTURES=120 -DCMAKE_BUILD_TYPE=Release
cmake --build build/ch35 -j
ctest --test-dir build/ch35 --output-on-failure
./build/ch35/multi_gpu_images --selftest
./build/ch35/multi_gpu_images
nvidia-smi topo -m
```

CTest 有两个用例：`ch35_partition_selftest` 验证 CPU 分区；`ch35_two_gpu_images` 在少于两张可见 CUDA GPU 时返回 77，CMake 设置 `SKIP_RETURN_CODE 77`，所以应显示 `Skipped`。两卡测试只有完整逐像素、求和、合并检查通过时才打印 `chapter 35 two-GPU images: PASS`。第 35 章的多 GPU 实践必须等真实双卡环境执行，单卡上的 CPU 自检或编译成功不能替代。

比较 1 卡和 2 卡总速度时，要量测相同四张图的**端到端时间**（创建上下文与资源可分列为一次性成本）、每卡 kernel 时间、上传下载时间、合并时间和同步等待；预热后重复，记录中位数/分布。图像太小，本例几千像素常被启动、拷贝和资源创建开销淹没；要换更大的批次并测试静态均分、按像素成本分配、动态队列。加速比用同一问题的 `T_1/T_2`，不能将两卡 kernel 耗时简单相加或只取最短那张卡的耗时。双卡还可能共享 PCIe/电源或受不同负载影响。

## 4. 常见错误

- 以为指针在所有设备可通用，忘记 `cudaSetDevice` 或在错误设备上创建 stream、释放内存。
- 只看 `cudaGetDeviceCount>=2`，不查拓扑/两个方向的 P2P 能力，直接解引用远端指针。
- 设备 1 的计算尚未完成，设备 0 就读取或复制其局部和。
- 多卡图片映射变更后没有同步修改局部偏移、全局编号、增益和 CPU 参考，导致“结果都在”却错位。
- 把单卡上的分区自检通过、或双卡用例 `Skipped`，写成 P2P/双卡实测通过。
- 小数据量的一次运行被用来断言多 GPU 一定加速；没有统计资源创建和跨设备合并成本。
- 普通 pageable 主机缓冲配合 `cudaMemcpyAsync` 就假定传输与计算会重叠；若需稳定重叠，应使用 pinned Host 缓冲并验证时间线。

## 5. 练习与参考答案

1. 图片编号 `0,1,2,3` 依 `image%2` 划分，两卡各处理哪些？答：设备 0 处理 0、2；设备 1 处理 1、3，局部编号均为 0、1。
2. 若设备 0 能访问设备 1，但反向不行，本例的 peer copy 能走哪条方向？答：代码的方向是把设备 1 的局部和复制到设备 0，并先在设备 0 启用访问设备 1；反向任务不能由这次能力查询推断可行。
3. 两设备 kernel 分别用 4 ms 和 6 ms，传输/合并/等待合计 3 ms，端到端时间至少该怎样估算？答：理想重叠下计算部分至少取较慢的 6 ms，加非重叠成本约 3 ms，为约 9 ms；实际要量测时间线，不能直接报 4 ms 或 10 ms。
4. CTest 显示分区自检通过、双卡用例 `Skipped`，本章什么已经验证、什么还没有？答：CPU 分区覆盖和布局逻辑已验证；双卡 kernel、跨设备资源、P2P、合并及性能都未验证。
5. 如果某张图片成本是其他图片的十倍，继续按图片数量均分是否合理？答：通常不合理；应按像素或预计处理成本重新分配，或者动态取任务，再量测每卡忙闲和总时间。
